# 一、脱壳的一般思路

脱壳是标准逆向流水线中的一个环节。完整流程是：

```
① 定位/采包        包名、版本、前台 Activity、pm path 拉 base.apk/split
② 静态侦察         zip 结构、Manifest 的 Application、dex 大小/数量、so、assets、框架指纹
③ 查壳/加固识别    壳类型、代际（一代/二代/三代）、加载方式
④ 脱壳   ←—— 本文主题
⑤ 反编译分析       jadx/apktool 还原 Java
⑥ 动态分析/hook    Frida/Xposed 打 native、加密、协议、风控
⑦ 算法/协议还原    unidbg 离线复现
```

把"脱壳"这一环再展开，它内部有 5 个阶段（后文 §2 对应标注）：

| 阶段 | 要做的事 | 关键问题 |
|---|---|---|
| **1. 查壳识别** | 判断壳类型/代际/版本，识别是"整体加密"还是"抽取式"还是 VMP | 是哪个厂的壳？几代？ |
| **2. 定位加载机制** | 找 DEX 由谁、在哪一刻被解密并交给 ART | native 解密？类加载器？ |
| **3. 选脱壳时机与 hook 点** | 按壳的加载机制选 hook 点（本例：ART `DefineClass`） | 在"解密后/定义前"这一瞬取 DEX |
| **4. 执行 dump + 修复** | 落盘；必要时修魔数/修方法体 | 拿到的必须是**完整可用**的 DEX |
| **5. 反编译验证** | jadx/baksmali 跑通、类名符号正常 | 产物能不能反编译 |

> **本文的落点**：他趣 = 阶段 1/2 查壳定位 → **阶段 3 hook ART `DefineClass`** → 阶段 4 落盘 → 阶段 5 校验。

## 1.1 壳的代际 → 对应脱壳手段

| 壳代际 | 原理 | 明文 DEX 能否直接取到 | 主用脱壳手段 |
|---|---|---|---|
| **一代（整体加密）** | 整个 DEX 加密；运行时解密成**完整 DEX** 再交给 ART | **有**（完整） | 内存搜索 `dex\n` / hook `open`·`mmap` / 读 `/proc/pid/mem`；难点在**时机 + 去重 + 有效性校验** |
| **二代（抽取式）** | DEX 结构保留，**方法体被抽空**，按需解密/回填 | **无**（只有壳骨架，dump 出来方法体是空的） | 必须 hook ART 加载/编译点（`ClassLinker::DefineClass`、`OpenMemory`、`DexFile` 构造）或主动调用触发补全（FART/Youpk/BlackDex） |
| **三代（VMP）** | 关键方法被替换为自定义虚拟机指令 | 无（非标准 DEX） | 还原虚拟机 / 指令级 Hook，属另一层话题 |

**通用做法**：无论哪种壳，**hook ART 加载点**（`DefineClass` 等）都最稳——在"类被定义"的那一刻，拿到的必然是**解密后、可用**的 DEX。

# 二、他趣实战记录

## 2.1 目标与环境

| 项 | 值 |
|---|---|
| 包名 / 版本 | `com.xingjiabi.shengsheng` / 8.6.9.5 |
| ABI | arm64-v8a |
| base.apk | `/data/app/~~D4dN9xQM63Ud-8hwL2ed8A==/com.xingjiabi.shengsheng-.../base.apk` |
| 设备 | Pixel 7 Pro，Android 16，KernelSU-Next + SUSFS |

## 2.2 查壳

静态看 APK（不解压，直接读 zip）即可定位壳：

| 证据 | 含义 |
|---|---|
| `lib/arm64-v8a/libnesec.so`、`libnesec-x86.so` | 网易易盾核心 so |
| `lib/arm64-v8a/libnshelper.so` | 易盾辅助 so |
| `lib/arm64-v8a/libxed.so` / `libxapo.so` | 疑似易盾 VMP/加固组件（按命名推断，未证实） |
| `assets/nedata.db`、`assets/nedig.properties` | 易盾资源 |
| `classes.dex` = **126,384,832 B**，头部却只有 **30 个类** | 壳的**加密容器**（不是真实业务 DEX） |
| `assets/resManager/*.xml` 大量 13B 文件 | 资源名混淆 |

对比：真实业务类（`cn/taqu/...`，数千个）在 APK 里**一个都看不到**。

**结论：网易易盾；真实业务 DEX 不在 APK 明文里，由壳在运行时生成/加载 → 必须 hook ART 加载点。**

## 2.3 定位加载机制与选 hook 点

- 易盾的 native so（`libnesec`）在进程内解密 DEX 后再交给 ART 加载（**具体用哪个类加载器本文未深究**，不影响选点）；
- ART 在把某个类"定义"出来时，一定会调用 `ClassLinker::DefineClass`，**此时该 DEX 已解密、base/size 有效**；
- 所以 hook 点选 **`libart.so` 的 `ClassLinker::DefineClass`**。

本机实测命中的符号（Android 16 / arm64）：

```
_ZN3art11ClassLinker11DefineClassEPNS_6ThreadEPKcmmNS_6HandleINS_6mirror11ClassLoaderEEERKNS_7DexFileERKNS_3dex8ClassDefE
```

> 注意与文章（Android 9）的签名差异：Android 16 的符号里**多了一个 `size_t` 参数**，且 `DexFile` 布局随版本变化——**不能照抄原脚本的写死参数下标/偏移**（见 2.5）。

## 2.4 前置障碍与对策

### 障碍 A：libnesec 的反 Frida 检测 → 秒崩

易盾会自建线程做反调试/反 Frida 扫描，直接 attach/spawn 挂脚本会导致进程 1 秒内 SIGSEGV。
**对策**：hook `libc` 的 `pthread_create`，凡是 `libnesec.so` 创建的线程，把其入口回调替换为空函数，让检测线程"空转"。

### 障碍 B：Frida server 与 Zygisk/Vector 注入冲突 → 秒崩

本机装有 Vector（Zygisk 版 Xposed），他趣在 `hk.kirk.trustme` 模块作用域内。
**Frida server 在跑 + 目标进程被 Zygisk 注入 = 内存写坏、秒崩**（与具体 app 无关）。
**对策**：把目标 app 移出 Vector 作用域。

```sh
# 查看某个模块的作用域
/data/adb/lspd/cli scope ls hk.kirk.trustme
# 移除他趣（pkg/user_id）
/data/adb/lspd/cli scope rm hk.kirk.trustme com.xingjiabi.shengsheng/0
```

### 障碍 C：Frida 自身特征

Frida 默认会暴露一批可被扫描的特征：`frida:rpc` 字符串、`frida-agent-*.so`/`frida-helper-*`、`gum-js-loop`/`gmain` 线程名、`@/frida-zymbiote-*` socket、默认端口 `27042`/`27043`、进程名 `frida-server`。
**对策**：用清掉这些特征的反检测版 frida-server（phantom-frida 17.16.4），并 **改名 + 非默认端口 + 只绑本地 + PC/设备版本严格一致**。

```powershell
# 设备端
adb push .\sysrender-server-17.16.4-android-arm64 /data/local/tmp/.sysrender2
adb shell su -c "chmod 755 /data/local/tmp/.sysrender2"
# 只绑本地 + 非默认端口
@'
nohup setsid /data/local/tmp/.sysrender2 -l 127.0.0.1:31337 >/data/local/tmp/.sysrender2.log 2>&1 < /dev/null &
'@ | adb shell su
# PC 端
adb forward tcp:31337 tcp:31337
frida-ps -H 127.0.0.1:31337
```

> PC 与设备版本必须一致（都是 17.16.4），否则 `Unable to communicate... major versions match`。

## 2.5 脱壳脚本

脚本位于本仓库 `frida/`：

| 文件 | 作用 |
|---|---|
| `frida/hook_libnesec.js` | hook `pthread_create`，中立化 libnesec 的检测线程 |
| `frida/dump_dex.js` | hook `ClassLinker::DefineClass`，取 DEX base/size 落盘 |
| `frida/run_dump.py` | 连设备、spawn、按序加载两个脚本、resume、打印日志 |

**相对文章原版的适配（Android 16 / Frida 17 必改）：**

1. **Frida 17 移除了 `Module.findExportByName/getExportByName` 静态方法**
   → 改用 `Process.getModuleByName("libc.so").getExportByName(...)`。
   （不改的话脚本加载即报 `TypeError: not a function`，hook 全不生效。）
2. **DexFile 布局跨版本不同**：不写死参数下标/固定偏移，改为在对象头若干指针里**自动定位指向 `dex\n` 的 `begin_`**；大小优先取 DEX 头 `file_size`（偏移 `0x20`），回退取 DexFile 内 `size_`。
3. **大 DEX 流式写盘**：用 `libc open/write` 分 1MB 块写，避免百 MB 级 DEX 在 JS 侧 `readByteArray` 爆内存。

执行：

```powershell
# 先杀 app，避免旧进程残留（设备端命令）
adb shell su -c "am force-stop com.xingjiabi.shengsheng"
# spawn 注入（脚本在 resume 前加载，确保 hook 早于应用代码）
py frida\run_dump.py
```

## 2.7 校验与反编译验证

### (1) 逐文件头校验（`_Temp/verify_dex.py`）

所有文件：magic=`dex\n`、`header_size=0x70`、`endian_tag=0x12345678`、`file_size == 实际长度`、
`checksum(Adler32)`/`signature(SHA1)` 自洽；DEX 版本 035/039。

> checksum/signature 在 dump 产物里仍能自洽，说明拿到的是**完整、未被截断**的 DEX 文件——这是"产物有效"的强证据。

样本：

```
file                          size    ver classes methods strings  chk sig fsz
02_0x7745778040.dex      126384832  035      30     847    1410   ok  ok  ok   ← 壳容器
03_0x76b665fffc.dex        8895424  035    7815   65535   60469   ok  ok  ok
28_0x7624da5b48.dex        2853580  039    4790   19422   21357   ok  ok  ok
...
total: ...
```

> `02` 与 APK 的 `classes.dex` 同尺寸（126,384,832 B）、同头（仅 30 类），即壳的**加密容器**，不是业务代码。

### (2) 业务类归属

按 Latin1 读字节 + 正则 `Lcn/taqu/`，命中大量业务类，例如：

```
02_0x7745778040.dex   cn/taqu=5898
03_0x76b665fffc.dex   cn/taqu=2743
06_0x76b445affc.dex   cn/taqu=446   com/xingjiabi=1106
```

### (3) jadx 反编译

```powershell
jadx -d _Temp\jadx-biz --no-res _Temp\dump_dex\03_0x76b665fffc.dex
```

- 单 DEX → **4503 个 .java**，目录结构清晰：`cn/taqu/{lib,library,module,shanlian}` + 三方库
- 文章关键类 `cn/taqu/lib/base/utils/AppAntiUtils.java` 完整还原：
  导入 `com.scottyab.rootbeer.RootBeer`、`initAnti()`、base64 字符串（`BTN_EXIT_TEXT=“退出应用”`）
- 2683 个类仅 34 个报错（≈1.3%，jadx 常态）

**结论：脱壳产物有效、可正常反编译，业务代码完整。**

## 2.8 结论

| 问题 | 结论 |
|---|---|
| 壳类型 | 网易易盾（`libnesec.so`），运行时解密生成并加载 DEX |
| 明文 DEX 从哪来 | **不在 APK 里**；`classes.dex`(126MB) 只是壳容器（仅 30 类），业务代码只能从运行时取 |
| 脱壳切入点 | hook ART `DefineClass`（在"DEX 定义"那一刻取解密后的 DEX） |
| 反 Frida | `pthread_create` 中立化 libnesec 线程 + phantom server 改名/换端口/本地绑定 |
| 产物 | 多个 DEX，全部校验通过，jadx 可反编译 |

# 三、踩坑记录

1. **Frida 17 API 变更**：`Module.findExportByName`/`getExportByName` 已移除，脚本必须改用
   `Process.getModuleByName(...).getExportByName(...)`，否则静默不生效、hook 全无。
2. **DefineClass 签名/偏移不能照抄**：Android 16 比 Android 9 **多一个 `size_t` 参数**，DexFile 布局也变了；
   用"自动定位 `dex\n`"最稳，别背偏移。
3. **Frida + Zygisk/Vector 冲突**：目标在 Vector 作用域内时，server 在跑 + 被注入 = 秒崩；
   先把 app 移出作用域（`lspd/cli scope rm`）再 spawn。
4. **`classes.dex` 是壳容器**：`02` 与 APK `classes.dex` 同尺寸，126MB 只有 30 个类，是密文容器，不含业务代码。
5. **二进制传输**：`adb pull` 的进度信息走 stderr，PowerShell 里别把它当成失败；大批量建议先
   `cp` 到 `/data/local/tmp` 再 pull。
6. **点遍各板块**：按需解密型壳只在类被首次使用时才解密，启动后应遍历各功能页，才能触发全部 DEX 加载。

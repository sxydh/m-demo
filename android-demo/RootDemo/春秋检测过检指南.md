# 春秋检测过检指南（Pixel 7 Pro / Android 16）

> 本文记录在一台 **Google Pixel 7 Pro（cheetah）、Android 16** 上，从零构建带 SUSFS 的
> KernelSU-Next 内核并逐项通过 **春秋 Native Check-Eros 4.5.3**（包名 `com.chunqiunativecheck`）的完整过程。
>
> 原则：所有改动可回滚；刷机前先备份原厂分区。
>
> 定位：只记录**关键步骤与坑**（顺序、判据、易错点、恢复），通用操作从略。

---

## 0. 适用场景与前置条件

### 0.1 前置条件（**开始前必须已具备，否则无法执行**）

| 条件 | 说明 / 检查命令 |
|---|---|
| 手机已解锁 Bootloader | `getprop ro.boot.flash.locked`（真实值应为 0） |
| 手机**已 root**（KernelSU 系） | `adb shell su -c id` → `uid=0` |
| 电脑有 adb/fastboot | `adb devices`、`fastboot --version` |
| 手机能连电脑 | USB 调试已开 |
| GitHub 账号 | 用于 Fork + Actions 构建内核 |
| 能下载原厂工厂镜像 | Google Pixel 工厂镜像站（做恢复备份用） |
| 手机能联网 | TA_enhanced 首次会联网拉 keybox；无网会退回 AOSP keybox，可能报 `AOSP 密钥` |

> 若你的手机**只勾了 OEM 解锁、BL 还没真正解锁**（或还没 root），先做 §0.4，再回到 §3。

### 0.4 从原厂到 root（BL 未解锁 / 尚未 root 时先做本节）

> 已解锁并已 root 的可跳过。本节只记**关键命令与坑**。

**A. 解锁 Bootloader —— ⚠️ 会清空全部数据**

```powershell
adb reboot bootloader
fastboot flashing unlock          # 手机上按音量键 + 电源确认
# 解锁触发 wipe；重启后重新走开机向导，并重新开启 USB 调试
```
- 坑：解锁前备份数据；解锁后 `ro.boot.flash.locked` 变 `0`、`verifiedbootstate` 变 `orange`（后面靠 TA/SUSFS 伪装）。
- 前提：开发者选项里“OEM 解锁”已可点亮（你已满足）。

**B. 准备与本机**完全同构建号**的原厂镜像**
- 到 Google Pixel 工厂镜像站（`developers.google.com/android/images`）下载与 `adb shell getprop ro.build.id` 一致的包（`cheetah-*.zip`）。
- 工厂包解压后里面还有一层 `image-*.zip`，**再解压一次**才得到各分区镜像：

```powershell
Expand-Archive .\cheetah-*.zip .\factory
Expand-Archive .\factory\image-*.zip .\factory\images
Get-ChildItem .\factory\images | Select-Object Name
```
- 首次 root 补丁打在 **`init_boot.img`**（Pixel 的内核在 `boot.img`，但 KernelSU 补的是 `init_boot`）。
- 坑：构建号不一致可能 bootloop；**务必保留原厂 `init_boot.img`** 做回滚。

**C. 首次 root（KernelSU-Next，LKM 模式）**

```powershell
# 1) 装「官方」KernelSU-Next 管理器（首次 root 用官方版更稳；spoofed 版留到 §6.2 换内核后再用）
#    来源：github.com/KernelSU-Next/KernelSU-Next/releases → KernelSU_Next_v3.3.0_*.apk
adb install -r ".\KernelSU_Next_v3.3.0_*.apk"

# 2) 打开管理器 → 安装(Install) → 选择原厂 init_boot.img → 生成 kernelsu_patched_*.img

# 3) 刷入（BL 已解锁）
adb reboot bootloader
fastboot flash init_boot kernelsu_patched_*.img
fastboot reboot

# 4) 验证
adb shell su -c id        # 期望 uid=0
```
- 坑：Pixel 7 Pro / Android 16 走 **init_boot**（不是 `boot`）。LKM 模式由内核加载 `kernelsu.ko`。
- 回滚：`fastboot flash init_boot init_boot.img`。
- 说明：这里先拿 LKM root，是为了能用 `ksud`/AK3 刷后面的自编译 SUSFS 内核（AK3 需要 root）。
  若你能自行产出带内核的 boot 镜像，也可解锁后直接用 `fastboot flash boot` 跳过本节。

> 完成本节后，从 **§3 采集本机参数** 继续（先 §4 备份，再 §5 构建/§6 刷内核）。

## 1. 检测项与原理对照

| 春秋检测项 | 判据（实测） | 过检手段 |
|---|---|---|
| Bootloader unlock / 启动状态异常 | 认证中的启动状态 / `ro.boot.*` 属性 | TA_enhanced 属性伪装 + TEESimulator 处理 target |
| Device has obtained ROOT access / abnormal module | 已加载 SELinux 策略含 `u:r:ksu:s0`、`ksu_file`、`magisk_file` 等关键字 | KSU `selinux_hide`（**开机前**启用并持久化） |
| Suspicious SELinux Policy | 同上 | 同上 |
| Third-party kernel | `uname -r/-v` 与预设名单/原厂不符（如 `...-WKSU`、构建时间 1970） | SUSFS `set_uname` 伪装为原厂串（post-fs-data 阶段） |
| Tampered Attestation Key(26) | 证书 patch 标签与系统属性不一致（安全补丁日期） | 让 `security_patch.txt` 与设备真实补丁一致 |
| USB debugging enabled | `settings global adb_enabled=1` | `settings put global adb_enabled 0`（本方案未用） |

> **重点**：`Tampered Attestation Key(26)` **与 keybox 是否被吊销无关**，本项目里最容易走错方向。

## 2. 总体方案

```
自建 GKI 内核（Google GKI 源码 + KernelSU-Next + SUSFS）
        │
        ├── KernelSU-Next 内置（GKI2 / 非 LKM）
        ├── NoMount 元模块（KernelSU-Next 新版需要 metamodule 才能挂载普通模块）
        ├── susfs4ksu 模块 + 升级后的 ksu_susfs（设置隐藏/伪装）
        └── 模块：Zygisk Next / Play Integrity Fix / TEESimulator-RS / TA_enhanced / HMA-OSS
```

关键配置：
- `/data/adb/tricky_store/security_patch.txt`（补丁日期）
- `/data/adb/tricky_store/target.txt`（TEESimulator 作用目标）
- `/data/adb/tricky_store/ta-enhanced/config.toml`（TA 配置，需关闭自动改补丁）
- `/data/adb/susfs4ksu/config.sh`（SUSFS 隐藏/伪装配置）
- `/data/adb/ksu/.feature_config`（KSU 内核功能位，如 `selinux_hide`）

> **adb/su 规范**：PowerShell 5.1 给 `adb.exe` 传参会丢内层引号，涉及 `su` 的多命令务必用
> here-string + 管道（`$cmd | adb shell su`），不要把命令写进 adb 参数。

## 4. 备份原厂分区（刷机前必做）

```sh
# 设备端（su）——注意把 <SLOT> 换成实际槽位，如 _b
OUT=/data/local/tmp/stock_bak
rm -rf $OUT; mkdir -p $OUT
for p in boot<SLOT> init_boot<SLOT> vendor_kernel_boot<SLOT> vbmeta<SLOT> dtbo<SLOT>; do
  dd if=/dev/block/by-name/$p of=$OUT/$p.img bs=1048576
done
sha256sum $OUT/*.img
```

```powershell
# 电脑端：保存到 RootDemo\stock_bak\<构建号>_slot_<槽>\
adb pull /data/local/tmp/stock_bak/. .\stock_bak\
Get-ChildItem .\stock_bak -Recurse -File | ForEach-Object { (Get-FileHash $_.FullName -Algorithm SHA256).Hash + "  " + $_.Name }
```

恢复（刷坏时）：
```
adb reboot bootloader
fastboot flash boot_b .\stock_bak\boot_b.img
fastboot flash vendor_kernel_boot_b .\stock_bak\vendor_kernel_boot_b.img
```

## 5. 构建 SUSFS 内核（GitHub Actions）

用 **WildKernels/GKI_KernelSU_SUSFS** 的 CI（GKI 源码 + KSU/SUSFS）：

1. Fork `https://github.com/WildKernels/GKI_KernelSU_SUSFS`。
2. Fork 的 `Settings → Actions → General → Workflow permissions` 设为 **Read and write**；
   Actions 标签页若提示，点 “I understand my workflows, go ahead and enable them”。
3. 运行 **Build Kernels**，参数：

| 输入（input 名） | 值 |
|---|---|
| Release Type (`release_type`) | `Action` |
| Use cache (`use_cache`) | `false`（首次） |
| Kernel Version (`kernel_build_version`) | `6.1.x-android14` |
| Patch date / sublevel (`os_patch_level`) | `124`（对应 2025-02，与本机 `6.1.124` 一致） |
| Kernel Branding (`brand_name`) | 任意（如 `WKSU`） |
| Commit mode (`commit_mode`) | `verified` |
| Root Flavor (`root_flavor`) | `KernelSU-Next` |
| Feature toggles | 保持默认（含 SUSFS / NoMount / BPF…） |

> 产物命名：`6.1.124-android14-2025-02-KernelSU-Next-AnyKernel3`。

**⚠️ 已知上游 Bug 与修复**：若构建在 `SUSFS` 步骤失败，报
`kernel_patches/pershoot/susfs4ksu/0001-*.patch: No such file or directory`
（`kernel_patches` 删了补丁，但 `.github/actions/susfs-setup/action.yml` 仍无条件引用）。
在 fork 中提交修复后重跑：

```yaml
# .github/actions/susfs-setup/action.yml：把两行 patch 改成“存在才应用”
for _p in "${{ github.workspace }}/kernel_patches/pershoot/susfs4ksu/0001-pershoot-Allow-core-to-be-built-with-no-features.patch" \
          "${{ github.workspace }}/kernel_patches/pershoot/susfs4ksu/0002-pershoot-Implement-SuSFS-and-Toolkit-coexistence.patch"; do
  if [ -f "$_p" ]; then patch -p1 < "$_p"; else echo "skip missing patch: $_p"; fi
done
```

构建成功后下载 **Artifacts**（需登录 GitHub；或 `gh run download`）：
- `*-AnyKernel3`（内核包）
- `*-BuildInfo`（校验信息）
- `KernelSU_Next_v3.3.0-*-spoofed_*.apk`（配套管理器）
- `NoMount-Metamodule`

#### 5.1 触发构建（两种方式）

**方式 A：Web** —— 仓库 `Actions` → `Build Kernels` → `Run workflow`，按上表填参数 → 运行。约 10–20 分钟。
> `release_type=Action` 时不会创建 Release，只在本次 run 里产生 Artifacts。

**方式 B：`gh` CLI（可脚本化/便于 AI 执行）**：

```bash
gh auth login
# 触发（把 <USER> 换成你的 GitHub 用户名）
gh workflow run main.yml -R <USER>/GKI_KernelSU_SUSFS --ref main \
  -f release_type=Action -f use_cache=false \
  -f kernel_build_version=6.1.x-android14 -f os_patch_level=124 \
  -f brand_name=WKSU -f commit_mode=verified -f root_flavor=KernelSU-Next

# 查看 / 等待
gh run list   -R <USER>/GKI_KernelSU_SUSFS --workflow main.yml --limit 5
gh run watch  <RUN_ID> -R <USER>/GKI_KernelSU_SUSFS --exit-status

# 下载产物到本地 .\artifacts
gh run download <RUN_ID> -R <USER>/GKI_KernelSU_SUSFS -D .\artifacts
```

> 构建流程：`resolve-sources` → `build-nomount-module` → `publish-manager-artifacts` → `build-android14-6-1`（内核）。
> 关键 job 名形如 `build-android14-6-1 (... 6.1.124-android14-2025-02 (KernelSU-Next))`。

#### 5.2 权限与自动化注意

- **Fine-grained Token 不能创建 Fork**，Fork 必须在网页手动点（或 classic token/`gh`）。
- 用 API/`gh` 触发工作流：token 需 **Actions: read/write**。
- 用 API 提交对 `.github/actions/*` 的修改：token 需 **Contents: read/write**（改 `.github/workflows/*` 才额外需要 `workflow` 权限）。
- 本指南用的自动化：Web 手动 Fork → API 启用 Actions + 触发 → API 改 `.github/actions/susfs-setup/action.yml` → 重新触发 → API 下载 artifacts。
- **产物格式坑**：Web 下载得到 `.zip`；`gh run download` 得到的是**目录**。而 `ksud module install` 和 AK3 需要 zip——
  请用 **7z/tar** 打包（**别用 `Compress-Archive`**：它写反斜杠路径，Android 端解压会坏）；AK3 也可把目录里的文件直接推到 `/data/local/tmp/ak3/`（无需再解压）。

把内核产物推到手机：
```powershell
adb push ".\6.1.124-android14-2025-02-KernelSU-Next-AnyKernel3.zip" /data/local/tmp/kernel.zip
```

## 6. 刷入内核 + 更换匹配的管理器（关键顺序）

### 6.1 刷内核（手动执行 AnyKernel3）

**注意**：社区里的 Sultan/Pixel 专属内核（如 `gs201-a16-...-Sultan-...`）与 Pixel 原厂 vendor 模块
**不兼容，会 `surfaceflinger` 崩溃 / bootloop**；**必须用通用 GKI 构建**。

```sh
# 设备端（su）
BIG=/data/adb/ksu/bin/busybox
rm -rf /data/local/tmp/ak3; mkdir -p /data/local/tmp/ak3
$BIG unzip -o /data/local/tmp/kernel.zip -d /data/local/tmp/ak3
cd /data/local/tmp/ak3
chmod -R 0755 tools; chmod 0755 anykernel.sh Image
mkdir -p bin
./tools/busybox --install -s /data/local/tmp/ak3/bin
for t in magiskboot magiskpolicy httools_static lptools_static snapshotupdater_static fec getevent; do
  ln -sf /data/local/tmp/ak3/tools/$t /data/local/tmp/ak3/bin/$t; done
export PATH=/data/local/tmp/ak3/bin:/data/local/tmp/ak3/tools:$PATH
OUTFD=1 BOOTMODE=true sh anykernel.sh
```
> 通用 GKI 的 `anykernel.sh` 只写 `boot`，不改 `vendor_kernel_boot`；
> `/postinstall/tmp` 不存在时 AK3 刷**活动槽**。

刷完**重启并验证**（此刻内核名还是自编译串，属正常）：

```powershell
adb reboot; Start-Sleep -Seconds 60
adb shell uname -r          # 期望 6.1.124-android14-...-WKSU
adb shell su -c id          # 仍应 uid=0；若失败，按 §6.2 安装匹配管理器后再试
```

### 6.2 更换/安装匹配的 KernelSU-Next 管理器

新内核是 KernelSU-Next（版本码如 `33271`），**旧管理器不匹配会导致 `su` 拒root、模块不挂载**。

1. 安装 spoofed 管理器 APK（包名是随机串，与旧 `me.weishu.kernelsu` 不冲突）：
   ```powershell
   adb install -r ".\KernelSU_Next_v3.3.0-*-spoofed_*.apk"
   ```
2. 打开它（`adb shell monkey -p <随机包名> 1` 或手动点），确认主页显示 `Working`。
   首次打开会把配套的 `ksud` 写入 `/data/adb/ksud`。
3. 卸载旧管理器（避免包名被检测到）：
   ```powershell
   adb uninstall me.weishu.kernelsu
   adb uninstall com.rifsxd.ksunext    # 若 §0.4 装的是官方 Next 管理器
   ```
   spoofed 管理器的包名是**随机串**（如 `wccygg.njrtqd.fbvelz`），每次构建都不同。
4. 重启；解锁后验证：
   ```powershell
   adb shell su -c id                 # uid=0
   adb shell su -c '/data/adb/ksud -V'   # uapi: 4
   ```
   （可选）内置 KSU 生效后，可刷回原厂 `init_boot.img` 去除 LKM 残留：
   `fastboot flash init_boot .\factory\images\init_boot.img`（非必须，本方案未做也能过）

## 7. 安装 NoMount 元模块（**不装则所有模块失效**）

KernelSU-Next 新版需要 **metamodule（元模块）** 才能挂载普通模块（管理器主页会显示
`Metamodule status: Not installed`）。

```powershell
adb push ".\NoMount-Metamodule.zip" /data/local/tmp/nomount-mod.zip   # 该产物本身就是可安装的模块 zip（zip 根目录即 module.prop/脚本）
adb shell su -c '/data/adb/ksud module install /data/local/tmp/nomount-mod.zip'
```
安装成功提示：`NoMount Internal API detected (Built-in)`，并创建 `/data/adb/metamodule` 软链。

> 安装后需**重启**，元模块才会开始挂载普通模块（后续 §9 的重启会一并生效）。

## 8. 安装 susfs4ksu 模块并**升级 ksu_susfs 二进制**（关键）

### 8.1 安装模块
```powershell
adb push ".\ksu_module_susfs_1.5.2+.zip" /data/local/tmp/susfs.zip   # 取自 sidex15/susfs4ksu-module Releases
adb shell su -c '/data/adb/ksud module install /data/local/tmp/susfs.zip'
```
模块会自动检测内核 SUSFS 版本，并用 `dmesg | grep "susfs:"` 判定是否生效。
**注意**：内核一旦有 SUSFS，模块才不会被自动 `disable`。

### 8.2 升级 ksu_susfs 二进制到与内核 SUSFS 匹配（v2.3.0）
模块自带的旧二进制对 SUSFS 2.x 会报 `SUSFS operation not supported`。用官方“通用二进制”替换：

```powershell
# 电脑端（可走代理）
Invoke-WebRequest -Uri "https://raw.githubusercontent.com/sidex15/susfs4ksu-binaries/universal-binary/ksu_susfs_arm64" -OutFile ksu_susfs_new
adb push ksu_susfs_new /data/local/tmp/ksu_susfs_new
```

## 10. 逐项过检

### 10.1 Bootloader unlock / 启动状态异常
- TA_enhanced 会在开机后伪装属性（`ro.boot.verifiedbootstate=green`、`ro.boot.flash.locked=1`、
  `ro.boot.vbmeta.device_state=locked` 等）。验证：`getprop ro.boot.verifiedbootstate` 应为 `green`。
- 在 `/data/adb/tricky_store/target.txt` 中加入检测器包名（TA 自动化通常会加所有三方应用）：
  ```
  com.chunqiunativecheck
  com.google.android.gms
  com.google.android.gsf
  com.android.vending
  ```

### 10.2 ROOT access / abnormal module + Suspicious SELinux Policy
**根因**：检测器读已加载 SELinux 策略，发现 `u:r:ksu:s0`、`u:object_r:ksu_file:s0`、
`u:r:magisk_file:s0`、`u:object_r:magisk_file:s0`。

**解法**：启用 KSU 内置 `selinux_hide`。**必须“开机时”就启用**（启动时备份 policydb），
运行时 `feature set` 会报 `EAGAIN/EBUSY`。正确流程：

```sh
# 设备端（su）
/data/adb/ksud feature set selinux_hide 1     # 运行时可能报 EAGAIN，但会写入配置
/data/adb/ksud feature save                   # 持久化到 .feature_config
# 重启手机
```
重启后确认：`/data/adb/ksud feature get selinux_hide` → `Value: 1 / Status: enabled`。

### 10.3 Third-party kernel / Tampered kernel
**根因**：`uname -r/-v` 暴露自编译名（如 `...-WKSU`）与异常构建时间（1970）。
**解法**：SUSFS `set_uname` 伪装为**本机原厂值**（§3 采集的）：

```sh
# /data/adb/susfs4ksu/config.sh
spoof_uname=2
kernel_version='<本机原厂 uname -r，如 6.1.124-android14-11-g8d713f9e8e7b-ab13202960>'
kernel_build='<本机原厂 uname -v，如 #1 SMP PREEMPT Wed Mar 12 13:40:07 UTC 2025>'
```
> `spoof_uname=1` 在 boot-completed 阶段；`=2` 在 post-fs-data 阶段（推荐，更早，且检测器
> “设备信息”里内核串也会变原厂）。

### 10.4 Tampered Attestation Key(26)（**别找错方向**）
**根因**：TEESimulator 生成证书时，证书 patch 标签与系统属性（安全补丁日期）**不一致**。
**不是** keybox 被吊销（那是 `证书已被吊销(CRL)` / `AOSP 密钥` 等其它条目）。

**解法**：让 `security_patch.txt` 与**本机真实补丁**一致，并关闭 TA 自动改补丁：

```sh
# 1) 关闭 TA_enhanced 自动改补丁：/data/adb/tricky_store/ta-enhanced/config.toml
#    [security_patch]
#    auto_update = false

# 2) 写 security_patch.txt（把日期换成 §3 采集的真实补丁）
#    system=YYYYMM（去掉横杠），boot/vendor=YYYY-MM-DD
printf '%s\n' 'system=202506' 'boot=2025-06-05' 'vendor=2025-06-05' \
  > /data/adb/tricky_store/security_patch.txt

# 3) 重启 TEESimulator 进程（无需重启手机）
kill -9 $(pidof TEESimulator)
```
> 备用：`system=prop` 会镜像设备属性。Pixel/Samsung “补丁日期为 05” 属正常。
> 注意：**魔改版 TEESimulator / 一键隐藏模块**也可能触发该项，尽量用原版。

### 10.5 USB debugging enabled（本方案保留）
```sh
su -c settings put global adb_enabled 0     # 关闭（会断 adb）
```
或写 `/data/adb/service.d/xx.sh` 开机自动关。

### 10.6 其他增强（预防性）
```sh
# GKI 推荐：开启 AVC 日志欺骗（与 SUSFS 的 avc_log_spoofing 互斥，二选一）
su -c '/data/adb/ksud feature set avc_spoof 1 && /data/adb/ksud feature save'
```
- SUSFS：`hide_loops`（默认开）、`hide_sus_mnts_for_all_or_non_su_procs=1`
- `/data/local/tmp`：属主 `shell:shell`、权限 `771`（`chown shell:shell /data/local/tmp; chmod 771 /data/local/tmp`）
- 可选：HMA-OSS 隐藏管理器/模块；存储空间隔离；FuseFixer

## 12. 恢复方案

### 12.1 内核回滚（fastboot）
```
adb reboot bootloader
fastboot flash boot_b .\stock_bak\boot_b.img
fastboot flash vendor_kernel_boot_b .\stock_bak\vendor_kernel_boot_b.img
fastboot reboot
```

### 12.2 模块问题
- KernelSU 安全模式：开机出现界面时**按住音量下**可停用所有模块。
- 卸载模块：`su -c '/data/adb/ksud module uninstall <id>'` 或删除 `/data/adb/modules/<id>`。

### 12.3 出错排查
- 内核名不是原厂串 → `spoof_uname` 配置/阶段不对（且需升级过 `ksu_susfs`）
- `selinux_hide` 为 disabled → 需 `feature save` 后重启
- `avc_spoof` 报 `EBUSY` → 与 SUSFS `avc_log_spoofing` 冲突，二选一（保留 KSU 版）
- 模块守护进程不启动 → 没装 NoMount 元模块，或管理器/ksud 与内核版本不匹配

## 13. 踩坑与注意

1. **Sultan/Pixel 专属内核不兼容**：会 `surfaceflinger` 崩溃 / bootloop，必须用通用 GKI 构建。
2. **KernelSU-Next 需要元模块**：不装 metamodule，所有普通模块都不挂载、守护进程不启动。
3. **管理器要与内核版本匹配**：内核更新后装同构建的 spoofed 管理器（本机旧 `32601` → 新 `33271`），
   它会把匹配的 `ksud`（uapi: 4）写入 `/data/adb`。
4. **`selinux_hide` 必须开机前启用**（先 set + save，再重启）。
5. **`Tampered Attestation Key(26)` = 补丁日期不一致**，不是 keybox。别往 keybox 上折腾。
6. **`avc_spoof` 与 SUSFS `avc_log_spoofing` 互斥**，同时开报 `EBUSY`。
7. **TA_enhanced 会自动改 `security_patch.txt`**：要固定补丁日期必须关它的 `auto_update`。
8. **susfs4ksu 自带二进制过旧**：对 SUSFS 2.x 会 `operation not supported`，必须升级 `ksu_susfs`。
9. **视频里的 `tee不可信.7z` 是腾讯 SOTER 专用**（卸载/隐藏 `com.tencent.soter.soterservice` + KPM hook），
   Pixel 没有 SOTER，对该项无意义。
10. **keybox**：公开的 AOSP / 共享 keybox（如 Yurikey）可能被吊销，触发 `证书已被吊销(CRL)` /
    `密钥证明未完成` 等条目；需“未吊销”的 keybox，与 (26) 无关。
11. **持久化**：`security_patch.txt`、`config.sh`、`.feature_config` 均已写入磁盘，重启不丢。
12. **重启后必须由用户手动解锁屏幕**，再继续下一步（未解锁时部分操作/界面检测异常）。

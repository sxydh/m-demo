# 项目周期与报价评估

> 适用场景：个人开发者承接网站、管理后台、App、小程序、桌面软件、自动化工具及企业应用。


## 一、核心原则

1. 不对一句话需求直接报固定总价。
2. 先确认交付范围和验收标准，再估人日、周期和价格。
3. 不确定部分先做付费预研，或单独按人日计费。
4. 价格谈不拢时减少范围，不直接压低日费率。
5. 周期谈不拢时减少功能，不用加班承诺弥补需求问题。
6. 估算的是“完成并通过验收”的时间，不只是编码时间。


## 二、第一次与客户沟通

第一次沟通的目标不是立即成交，而是判断：

- 客户真正要解决什么问题；
- 谁是使用者，谁有决策权，谁负责验收；
- 第一阶段必须交付什么；
- 客户的预算和时间是否现实；
- 项目依赖是否具备；
- 哪些地方存在较大不确定性。

建议让客户提前提供：

- 需求文档、原型、截图或参考产品；
- 当前业务的操作录屏；
- 现有系统、接口文档和测试环境；
- 示例数据和测试账号；
- 期望上线时间和预算区间。

第一次会议可以按以下顺序提问：

1. 这个项目要解决什么业务问题？
2. 谁使用？每天大约多少用户、数据或订单？
3. 现在的完整操作流程是什么？
4. 当前最痛的三个问题是什么？
5. 第一版必须具备的三个功能是什么？
6. 哪些功能可以放到第二期？
7. 需要对接哪些系统、硬件或第三方平台？
8. 客户能提供哪些接口、账号、数据和测试环境？
9. 失败、重复、超时、断网、误操作时应该怎样处理？
10. 什么时候必须上线，为什么是这个时间？
11. 谁最终验收，什么结果算验收通过？
12. 预算大致在哪个区间？
13. 上线后需要怎样的维护和响应速度？

开场话术：

> 我先了解业务目标、使用流程、必须功能、外部依赖和验收条件。范围确认后，我再给正式报价和周期，这样可以避免后续因为双方理解不同而反复加需求。

如果客户不愿透露预算，可以问：

> 为了避免方案和预算相差太远，这个项目更接近 2 万、5 万还是 10 万以上？不同预算对应的第一期范围会不同。


## 三、把模糊需求变成可估算范围

不要用“做一个商城”“做一个 App”作为估算单位。先拆成用户可以完成的业务流程，例如：

- 用户注册、登录、找回密码；
- 创建、修改、取消订单；
- 管理员审核和查询订单；
- 支付、退款和对账；
- 导入、导出和统计；
- 消息通知；
- 部署、备份和日志查询。

每个功能至少写清：

- 谁使用；
- 输入是什么；
- 正常流程是什么；
- 异常流程是什么；
- 数据保存在哪里；
- 是否依赖第三方；
- 怎样验收。

把任务继续拆到 0.5～2 人日。单项超过 2～3 天，通常说明拆得还不够细。


## 四、人日估算方法

对每个任务分别给出三个数字：

- O：乐观时间；
- M：最可能时间；
- P：悲观时间。

期望人日公式：

```text
期望人日 = (O + 4M + P) / 6
```

示例：一个第三方登录接口，乐观 0.5 天、最可能 1 天、悲观 3 天：

```text
(0.5 + 4 × 1 + 3) / 6 = 1.25 人日
```

项目总人日不能只包含编码，还应加入：

- 需求沟通和方案：5%～15%；
- 自测、联调和回归：15%～25%；
- 部署、文档和交付：5%～10%；
- 项目管理和客户沟通：5%～10%；
- 风险缓冲：10%～30%。

推荐公式：

```text
基础人日 = 所有任务期望人日之和
交付人日 = 基础人日 + 测试 + 联调 + 部署 + 文档
报价人日 = 交付人日 × (1 + 风险系数)
```

风险系数参考：

- 需求清楚、完全做过、无第三方依赖：10%；
- 普通业务系统、有少量接口联调：15%～20%；
- 需求有变动、多人联调或环境复杂：20%～30%；
- 技术没验证、依赖外部平台或政策：不要直接包死，先预研。


## 五、日历周期怎么算

人日不等于自然日。个人开发者还需要处理沟通、会议、修改、部署和其他事务。

建议按每周 4 个有效开发日计算：

```text
开发周数 = 报价人日 / 4
对外周期 = 开发周数 + 等待联调和验收的时间
```

例如报价工作量为 32 人日：

```text
32 / 4 = 8 周
```

对外可以承诺 8～9 周，而不是 32 个自然日。

影响周期但不一定增加人日的事项：

- 客户反馈需要等待；
- 接口、账号或素材不能及时提供；
- 应用市场或第三方审核；
- 客户只能在固定时间验收；
- 多方联调需要排期。

合同中应写明：因甲方资料、接口、账号或反馈延迟，交付日期顺延。


## 六、日费率与报价

个人开发者不能使用“工资除以 22 天”作为日费率，因为一年不可能每天都有付费项目。

日费率公式：

```text
日费率 =（目标年收入 + 社保税费 + 设备软件 + 空档成本）/ 年可售卖人日
```

个人开发者一年通常只有 120～160 个可售卖人日。

示例：

```text
目标年收入             300,000 元
社保、税费、设备等      60,000 元
年可售卖人日               150 天
最低日费率 = 360,000 / 150 = 2,400 元/天
```

正式报价公式：

```text
项目报价 = 报价人日 × 日费率 + 第三方费用 + 固定风险费用
```

准备三个价格：

- 底价：低于这个价格不值得接；
- 目标价：正常利润并包含合理风险；
- 理想价：客户要求更高质量、响应速度或更短周期时使用。

不要把底价直接报给客户。目标价应给谈判留出约 10% 的空间。


## 七、AI 如何计入估算

AI 通常能缩短：

- 常规 CRUD；
- DTO、表单和接口样板代码；
- SQL、脚本和基础测试；
- 文档、代码阅读和普通重构。

AI 很难明显缩短：

- 需求澄清；
- 业务规则确认；
- 第三方接口等待；
- 线上问题复现；
- 跨系统联调；
- 验收和需求变更；
- 安全、数据一致性和异常恢复。

建议只对熟悉、可验证的编码任务乘 0.6～0.8；对沟通、联调、部署和未知风险不打折。

客户购买的是交付结果，不是你的键盘工作时间。AI 提高效率可以成为你的利润和竞争力，不必全部作为降价让给客户。


## 八、选择合适的报价方式

### 1. 固定总价

适合：范围明确、验收明确、技术成熟的小项目。

要求：必须写清包含项、排除项和变更规则。

### 2. 分阶段固定价

适合：中大型项目，也是个人开发者最推荐的方式。

示例：

- 阶段一：需求和原型；
- 阶段二：核心业务功能；
- 阶段三：第三方集成；
- 阶段四：测试、部署和验收。

每阶段独立报价、交付、验收和收款。

### 3. 按人日计费

适合：需求会持续变化、长期维护或客户无法提前确定范围。

需要约定日费率、工时记录方式、每周上限和结算周期。

### 4. 付费预研

适合：新技术、第三方平台、硬件、算法、支付、爬虫或自动化等高风险需求。

通常为 2～5 天，交付内容包括：

- 可行性验证；
- 原型或最小技术样例；
- 风险清单；
- 功能边界；
- 正式周期和报价。

预研费用可以约定在签正式项目后部分抵扣，但不要免费做完整方案。


## 九、报价单必须包含什么

1. 项目目标；
2. 本期包含的功能；
3. 明确排除的功能；
4. 支持的平台、设备、浏览器和版本；
5. 甲方需要提供的接口、账号、数据和素材；
6. 每个阶段的交付物；
7. 验收标准；
8. 周期及开始条件；
9. 报价和付款节点；
10. 免费修改次数或缺陷修复期；
11. 新需求的计费方式；
12. 第三方费用由谁承担；
13. 源码、部署和知识产权范围；
14. 项目暂停、取消和延期的处理方式。


## 十、需求变更规则

以下通常属于缺陷，应免费修复：

- 已确认功能没有按验收标准工作；
- 已约定环境中出现可重复的软件错误。

以下通常属于新需求，应重新报价：

- 新增页面、角色、流程或字段；
- 改变已经确认的业务规则；
- 新增第三方平台或运行环境；
- 因第三方接口变更而重新开发；
- 验收后改变交互或视觉方案；
- 提升原来没有约定的性能、并发或安全等级。

变更处理流程：

```text
客户提出变更
→ 开发者说明影响
→ 确认新增费用和顺延时间
→ 客户书面确认
→ 开始实施
```


## 十一、付款建议

小项目：

```text
50% 启动 + 50% 交付
```

中型项目：

```text
30% 启动 + 40% 核心版本 + 30% 最终验收
```

长期项目：

```text
按周、双周或月结，避免全部费用压到最后。
```

每个付款节点都要对应明确的交付物。不要在没有首付款的情况下开始大规模开发。


## 十二、降低报价但不亏损

客户预算不足时，可以：

- 只做核心流程；
- 减少角色、页面或报表；
- 使用成熟组件，不做定制设计；
- 第一阶段只支持一种平台；
- 减少第三方集成；
- 把低优先级功能移到第二期；
- 缩短免费维护期；
- 改为按人日结算。

不要同时接受：完整范围、低价格、短周期和无限修改。


## 十三、危险信号

- “先做出来再谈钱”；
- “功能很简单，你先报个最低价”；
- 不愿确认功能范围和验收标准；
- 没有测试账号、数据或接口，却要求固定日期交付；
- 联系人不能决定需求和验收；
- 不断增加功能，却认为都属于原需求；
- 要求先交完整源码再付款；
- 要求长期免费维护；
- 预算明显低于工作量，却不愿减少范围。

出现这些情况时，优先改为付费预研、阶段交付或按人日结算。

## 十六、项目结束后的复盘

每个项目都记录：

- 原估人日；
- 实际人日；
- 差异最大的任务；
- 返工原因；
- 等待客户和第三方的时间；
- AI 实际节省了哪些工作；
- 下次应调整的系数。

连续记录 3～5 个项目后，你自己的历史数据会比任何通用行业报价更准确。


## 最终检查清单

报价前确认：

- [ ] 目标和核心流程已经写清
- [ ] 包含项与排除项已经写清
- [ ] 验收人和验收标准已经确认
- [ ] 外部依赖和甲方责任已经确认
- [ ] 不确定部分已经预研或单独计费
- [ ] 已包含测试、联调、部署和沟通时间
- [ ] 已加入合理风险缓冲
- [ ] 付款节点对应明确交付物
- [ ] 需求变更有书面处理规则
- [ ] 当前报价不低于自己的底价

估算不可能百分之百准确。专业的做法不是猜中一个数字，而是通过范围确认、分阶段交付、付费预研和变更规则，把估算误差控制在双方都能承担的范围内。
